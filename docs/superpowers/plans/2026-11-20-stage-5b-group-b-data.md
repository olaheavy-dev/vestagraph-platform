# Stage 5b group B (data): implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the data pipeline's core (editions, checks, switch live, roll back), the licence register, freshness alerts, our own postcode lookup, two model sources end to end (crime and flood risk by postcode), the walking-time build (Sheffield, then England), and Dagster to run it, so every other source is then a small ticket in the same pattern.

**Architecture:** A plain Python package, `vestagraph-pipeline`, holds everything that decides anything (adapters, tidy, checks, editions, switching, freshness, postcode lookup) and never imports Dagster. Each source's edition is its own table in the `area` schema, loaded by streaming (`COPY`), checked with SQL and streaming counters over the loaded table, and made live by switching a `_current` view; one per-source lock covers numbering, loading, checking and switching. A separate `vestagraph-dagster` package wraps the core. Heavy builds run on GitHub Actions and hand results back as artifacts that the server pulls only from verified `main` runs; no database credential lives in GitHub.

**Tech Stack:** Python 3.14, psycopg 3 (with psycopg-binary and psycopg-pool), SQLAlchemy 2 (Core) and Alembic (0062), boto3 (R2) and githubkit (GitHub) (BE-41), Frictionless Table Schema for each source's column rules, PostgreSQL with PostGIS (Neon in production, a throwaway PostGIS container in tests), Dagster 1.x with SQLite run storage (0061), Valhalla (container image), GitHub Actions, Cloudflare R2.

**Spec:** [`docs/superpowers/specs/2026-11-20-stage-5b-data-design.md`](../specs/2026-11-20-stage-5b-data-design.md); decisions [0061](../../decisions/0061-pilot-data-pipeline-postcodes-and-walking-times.md) (with its dated choices: live flood warnings left the pilot) and [0062](../../decisions/0062-database-packages-and-test-database.md).

**When:** written 20 Nov 2026; **built after groups C and D are decided** (0046, 0061), after group A's build ([plan](2026-11-20-stage-5b-group-a-foundation.md)), whose Task 9 measures the server's free memory (this plan's Task 9 stop point) and whose Task 10 creates the Neon project, the `area` and `personal` schemas, PostGIS and the role `vestagraph_app`.

## Global Constraints
- No pilot source goes live unless its register record says `cleared`, and only the founder sets `cleared`, case by case (0061).
- A failed edition never goes live; the live edition stays. A rolled-back edition's content is `rejected` and never goes live again automatically. Missing values stay missing (never zero, rule 7); an empty answer is valid only where the record says so.
- Every calculated figure shown comes from `vestagraph_area` (rule 2); SQL selects, filters and checks inputs only. Walking times are an input (DA-18): stored as Valhalla's **seconds**, with their method and OpenStreetMap date; `vestagraph_area` rounds them for display.
- Freshness counts from the last **confirmed** fetch: content that passed every check, or matched an edition that already passed; a fetch that fails tidy, checks or switch leaves it unchanged (0061).
- Keep 3 passed editions per source, 2 for the big ones (walking times, the postcode directory, bus timetable inputs). Row-change limit: a change of **more than** 20% fails, unless the record says otherwise.
- Memory: the server may have only about 1.5 GB free. Never hold a whole source in memory: fetch to a file, tidy as an iterator, load with `COPY`, check with SQL or streaming counters.
- No database credential in GitHub; GitHub jobs return artifacts that the server pulls only from a successful `workflow_dispatch` run on `main` of the named workflow (0061). The data-build and publish workflows are founder merges, added to `AGENTS.md`'s founder-merge list in Task 1.
- Searched postcodes never leave our systems or reach a log or an error message (0046): every engine is created with `hide_parameters=True`.
- Database identifiers are built with `psycopg.sql.Identifier` from register ids mapped to `[a-z0-9_]` (never string formatting).
- The pipeline and migrations use the **direct** (unpooled) connection, `DATABASE_URL_DIRECT` (group A plan); the API uses the pooled one. Migrations run as the role `vestagraph_app`.
- Packages (0061, 0062, BE-41): `psycopg[binary,pool]` 3.x, `sqlalchemy` 2.x, `alembic` 1.x, `dagster`, `dagster-webserver`, `boto3`, `githubkit`. Anything else is proposed to the founder in its pull request with evidence (WW-25). Founder merges: Task 1 (CI and the licence exception), Task 8 and Task 8b (workflows), Task 9 (`deploy/`).
- Test names `test_<method>_<condition>_<result>`; `make check` passes after every task; test expectations are worked out by hand, with their working (rule 2); boundary cases follow decision 0034.

## Review Focus
1. **Two runs on the same source at once** (an overlapping run and a rollback, or a Dagster retry): the second waits for the lock; edition numbers never collide; the view is never missing (Task 3).
2. **A publisher's file changes shape** (a renamed or missing column): the edition fails with a named reason, the live one stays, the failure alert fires, and the source goes late if it keeps happening (Tasks 3, 5, 6).
3. **A rolled-back file is fetched again**: it is not promoted; the first time, the failure is recorded and alerted once; after that the live edition stays and the source goes `late` in the normal way until the publisher sends a new file (Tasks 3, 5).
4. **A postcode typed in any case or spacing** ("nb14xy", " NB1  4XY ") finds the same row; a malformed one is "not a postcode", never "unknown"; a database error during lookup never shows the postcode (Tasks 1, 7).
5. **A walking route that doesn't exist** is `no_route`, a place the build didn't reach is `not_computed`; neither is ever shown as 0 minutes (Task 8).

### Task 3: Editions, checks, switch live, roll back
**Files:** Create `src/vestagraph_pipeline/editions.py`, `checks.py`; Test `tests/test_pipeline_editions.py`, `tests/test_pipeline_checks.py`.

**Interfaces:**
- `source_lock(conn, source: str)`: a context manager taking a session-level `pg_advisory_lock` on the direct connection (released in `finally`); every function below runs inside it.
- `load_candidate(conn, source: str, rows: Iterable[tuple], columns: Sequence[str], raw_sha256: str, publisher_date: date | None, run_ref: str | None) -> int`: allocates the next edition number under the lock, creates the table, streams rows with `COPY`, writes `row_count` and an `editions` row with status `candidate`, all in one transaction: on any exception (a `TidyError` raised while rows stream in included) nothing is left behind and the error is re-raised.
- `CheckResult(name: str, passed: bool, detail: str)`; `run_checks(conn, source: str, edition: int, record: SourceRecord) -> list[CheckResult]`: reads the record's Table Schema and checks, as SQL over the candidate table, that every field is present and each constraint holds (`required` → no nulls, `enum`, `minimum`/`maximum`, `pattern`), and the row-change limit against the live edition's `row_count`; an empty table fails unless `emptyIsValid`. Stores the results in `editions.checks` and sets status `failed` if any failed. A failed edition's table is dropped at once (its raw file and `editions` row stay).
- `_make_live(conn, source: str, edition: int, replaced_status: Literal["retired","rejected"]) -> None` (internal, the one place that switches): in one transaction drops and recreates the view, marks the edition `live` and the one it replaces `replaced_status`; then prunes passed editions beyond 3 (2 when `bigSource`), never the live one. Each public entry point checks its own allowed starting status first and refuses any edition whose checks did not all pass (`EditionNotPassed`):
- `switch_live(conn, source: str, edition: int) -> None`: only from `candidate`; calls `_make_live(..., "retired")`.
- `rollback(conn, source: str, to_edition: int) -> None`: only from `retired`; calls `_make_live(..., "rejected")`.
- `restore_edition(conn, source: str, edition: int) -> None`: the operator's deliberate undo of a roll-back (run only from the founder-started `restore_job`): only from `rejected`; calls `_make_live(..., "retired")`, so the edition it replaces goes back to `retired` and can be rolled back to again; refuses an edition that failed its checks. Nothing automatic ever calls it (`run_source` never promotes rejected content).

### Task 5: Running a source and freshness
**Files:** Create `src/vestagraph_pipeline/run.py`, `freshness.py`; Test `tests/test_pipeline_run.py`, `tests/test_pipeline_freshness.py`.

**Interfaces:**
- `Adapter` protocol: `fetch(dest: Path) -> None`; `tidy(raw: Path) -> TidyResult(columns: Sequence[str], rows: Iterator[tuple], publisher_date: date | None)` (raises `TidyError` with a reason).
- `run_source(conn, store: RawStore, record: SourceRecord, adapter: Adapter, now: datetime) -> RunOutcome` (`unchanged` | `live` | `rejected-content` | `failed`): `require_cleared`; fetch to a temporary file; under `source_lock`: if the hash matches the live edition, confirm (`unchanged`); if it matches a `rejected` edition, do not load (`rejected-content`): when `last_failure` does not already name this hash, set `last_run_ok = false` and `last_failure = "rejected-content:<sha256>"` (one alert); when it already names the same hash, set `last_run_ok = true` and leave `last_failure` and `last_confirmed_at` unchanged, so the state shows `fresh` until the allowed age (counted from the last confirmed fetch) runs out and then `late`, rather than alerting every run; a genuine `failed` run in between replaces `last_failure`, so the next rejected run alerts again; only `unchanged` or `live` clears `last_failure`; else store raw, tidy, `load_candidate`, `run_checks`, `switch_live`, and for a big source `store.drop_after_live`. On `unchanged` or `live`: `last_confirmed_at = now`, `last_run_ok = true`, clear `last_failure`. On `failed`: `last_run_ok = false`, `last_failure` set.
- `freshness(conn, register, now: datetime) -> dict[str, Literal["fresh","late","failing"]]` for **cleared sources that have been live at least once** only: `failing` when `last_run_ok` is false (wins over `late`); `late` when `now - last_confirmed_at > allowedAge`; else `fresh`.
- `write_state_file(path: Path, states) -> None`: JSON of source ids and states only, written atomically. The API's `/healthz/data` (#93) serves it; nothing reads the database per request.
